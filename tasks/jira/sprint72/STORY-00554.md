# STORY-00554: 非 tracking 时后台定时器 pause

**Epic**: E-Battery · **Sprint**: 72 · **Points**: 2 · **Owner**: Frontend · **Status**: Done

## Description
When the app is in background AND the user is not currently tracking, all periodic timers (network drain, incremental flush, dynamic sampling reeval) should pause. Tracking-active state = timers keep running (user is hiking, we need them).

## 现状根因
`useTrackingStore.ts:393-465`:
- `drainInterval` (1s 轮询后台 queue) - 后台也跑
- `incrementalFlushInterval` (120s PATCH 服务器) - 后台也跑
- `dynamicSamplingInterval` (10s 重算 GPS 采样) - 后台也跑

只靠 `if (status !== 'tracking') return` 单点判断，但**该判断在 tracking 中 status=tracking**，所以定时器持续跑。设计初衷是"tracking 时该跑"，问题是——**没 tracking 时定时器仍在**（因为 tracking 结束后没显式 pause）。

调研后修正：现有代码 `startTracking` 时才 start 这些 interval，`stopTracking` 时会 clear。所以**"非 tracking 时定时器已经不在"是现状**。真正的问题是：**tracking 中 + AppState=background 时定时器全跑，是不是必要**？

判断：
- `drainInterval` — 后台 queue drain，tracking 中必要（存 GPS 点）
- `incrementalFlushInterval` — 120s PATCH 服务器，tracking 中可保留但可以延长后台间隔
- `dynamicSamplingInterval` — 10s 重算，tracking 中 background 时可延长到 30s

**改法**（保守）:
1. 保持 tracking 时所有定时器运行（安全）
2. **后台时** `incrementalFlushInterval` 从 120s → 300s（省网络电）
3. **后台时** `dynamicSamplingInterval` 从 10s → 30s（省 CPU）
4. AppState=active 立即恢复原间隔（用户看轨迹要新数据）
