## Description

As Cairn DevOps, I need to set up a weekly cron job that cleans up orphan rows in `hidden_items` (where the referenced mark/route has been deleted), since `hidden_items` doesn't have FK on `item_id` (intentional design per v4 plan §6).

## Expected Result

`node-cron` registered in `backend/src/index.js` runs every Sunday 3am cleaning orphans. `TECH_SPEC.md` has `§cron` documenting decision. Runs log to `backend/logs/cron.log`.

### Decision: in-process cron (not sidecar)
v1 has exactly one job (weekly orphan cleanup). In-process node-cron is simpler; container restart misses one cycle at worst (idempotent — next Sunday catches up). If v2 adds more jobs or strict SLA needed, revisit.

### Implementation note (mid-Sprint debugging)
First implementation used `DELETE h FROM hidden_items h LEFT JOIN ... LIMIT 1000` — MySQL does NOT allow LIMIT on multi-table DELETE with JOIN. Fixed by 2-step pattern: SELECT orphan tuples (LIMIT respected) → DELETE by tuple in a transaction. Comment in module documents the constraint.

### Container persistence note
Same as Story-528: index.js was patched in the live container via `patch_container_cron.js`. Future image rebuild must include the local commit's source. The patch script is idempotent and can be re-run safely.
