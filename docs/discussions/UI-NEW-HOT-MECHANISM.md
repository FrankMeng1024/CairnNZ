# UI: 新 mark 出生救济机制（NEW + HOT 浮动）

**记录时间**: 2026-05-31
**来源**: 算法 case 测试中发现"Zoe 海豹 mark"问题——新 mark 因 UI 聚类被淹没

## 背景问题

Wellington Red Rocks 海豹观察区 case：
- 月流量 1500 人
- 同位置已有 12 个同类型 mark
- 新用户标的 mark 被 UI 自动聚类淹没
- 4 个月持续 0 互动

**根因**：算法层无能为力——它从来看不到这个 mark 已经被 UI 隐藏了。

## 决议方向

**算法层不动**（保持 5000 random 100% 通过率），UI 层负责曝光救济。

## UI 应实现的两个机制

### 机制 1：创建时反摩擦（同类高密度提示）

```
用户点"创建 mark" → 系统检测 50m 半径
  → 已有 ≥ 3 个同类型 mark
    → 弹窗: 「这地方已有 N 个 supply mark：[列表]
              想先看看现有的吗？还是确实要新建？」
    → 提供"给现有 mark 点赞"快捷入口
  → 用户仍坚持创建: 进入下一步
```

### 机制 2：新 mark 出生救济（NEW 浮动 + 聚类优先）

```
mark 创建后进入"出生期":
  - 时间窗: 30 天 OR 直到累积 likes >= 1 OR reports >= 1
  - UI 聚类规则:
    * 出生期 mark 显示 "NEW" 徽章
    * 同类聚类时, 出生期 mark 浮在顶层
    * 聚类点开时, 出生期 mark 排序在前
  - 出生期结束: 回到正常 UI 聚类顺序
```

## 不实现的方向（已讨论排除）

- ❌ **算法层加出生期心跳**: 会破坏 chaos-monkey 5000 random 100% 通过率, 把"出生时间"这种元数据混入纯粹的"用户行为评价"算法是关注点不分离
- ❌ **强制不允许新建重复 mark**: 太重, 有时同地点不同内容是合理的（日出点 vs 日落点）

## 后续可考虑

- 个人 mark vs 公共 mark 二元入口（用户犹豫时默认私人, 攒够朋友赞后转公共）
- 这是另一个产品方向, 跟"新 mark 淹没"不直接相关, 单独讨论

## 实施时机

UI 改造 sprint 时执行, 不阻塞当前算法工作。
