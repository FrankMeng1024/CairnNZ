# Public Marker 反馈机制 — v3 方案

**Version**: 3.0
**Created**: 2026-05-30
**Status**: 讨论稿，待用户确认后落 PRD4
**Scope**: 仅讨论 public marker 的赞 / 举报 / 展示 / 寿命算法。route 私人 / group only，不在范围。

---

## 0. 已锁定的边界（不再讨论）

| 边界 | 决定 |
|---|---|
| route 是否 public | **否**，永远私人 / group only |
| public 范围 | 仅 marker（cairn / pin） |
| personal / group marker 是否点赞 | **否**，零反馈机制 |
| 投票身份是否公开 | **完全匿名**（DS 同源），后端记录用于风控 |
| 是否有"踩" | **否**。沉底靠时间衰减 + 独立举报通道 |
| 是否有评分 / 评论 | **否** |

---

## 1. 反馈形态（最终）

```
public marker 上的反馈机制 = 1 + 1:
  ❤  匿名 Like      —— 唯一投票动作
  🚩 独立 Report    —— 仅针对违规内容（不计入投票）

不存在: 踩 / 评分 / 评论 / 转发
```

**Like 视觉**：用 Cairn 石堆 logo 的微缩图标（不用红心，避免 Strava-like 符号）。色调 sepia 棕（与 PRD3 E-016 DOC 橙色族协调），**填充 = 已点过**，**线框 = 未点过**。

**Report 视觉**：低调旗帜图标，置于 detail sheet 底部"More" 折叠区，不与 Like 同层显示——**降低误触 + 不暗示对抗性**。

---

## 2. 距离分层（3 段，已精简）

> 来自 v2 的 5 段简化为 3 段——避免 30-100m 的临界跳变体验突兀。

| 距离 | 渲染 | 操作 |
|---|---|---|
| **> 500m** | 不渲染 | - |
| **30-500m** | 聚类点 + 数字（远）/ 弱化显示赞数（中） | 不可投票 |
| **< 30m** | 完整 detail + AR 渲染 | 可投票 + 可修改 |

> **临界过渡**：当用户从 30-500m 进入 < 30m 时，detail sheet 顶部出现**淡入式提示**"你已到达，可以为这个 cairn 留下标记了"——给用户清晰的状态切换反馈。

---

## 3. 投票触发条件

| 条件 | 规则 |
|---|---|
| **路过验证** | 用户 trackPoints 在过去 ≤ 7 天内有点位经过该 marker 30m 半径 |
| **当前距离** | 投票时刻 GPS 距离 < 30m |
| **任一满足即可** | 路过验证（解决离线场景）或 实时距离（解决实时场景） |

> **离线场景解决**：NZ 大量步道无信号。用户 hike 时离线路过 marker，3 天后回家想点赞——只要 trackPoints 在 7 天内经过，**允许事后投票**。trackPoints 同步上后端时验证。

> **7 天窗口**：超过 7 天后路过记忆失效，避免远距离回忆型乱投。

---

## 4. 修改 / 撤销

| 维度 | 规则 |
|---|---|
| **改"已 Like" → 撤销** | 任何时候可撤（< 30m **或** 距投票 < 24h） |
| **撤销后再 Like 同 marker** | 该账号对该 marker 总投票配额 -1（防"反复刷续命"） |
| **每 marker 同账号最多投票次数** | 3 次（撤+重投+撤+重投+撤+重投，到顶） |

> v2 的"30m **or** 3h"窗口太短（步行 30m 30 秒就出去了，3h 太赶）。改为 **30m or 24h**——给"路过后突然想撤"留余地。

## 5. 数学公式（最终，已修复 v2 漏洞）

### 5.1 输入

| 符号 | 含义 |
|---|---|
| `L` | 该 marker 的 Like 数（去重，每账号 1 票） |
| `t_create` | marker 创建时间 |
| `t_last_like` | 最近一次 Like 时间（**L=0 时定义为 t_create**，修复 v2 漏洞） |
| `Δt` | 当前时间 - max(t_create, t_last_like) |
| `H_type` | 该类型半衰期（per-type） |
| `is_winter` | 该 marker 所在区域是否在季节性休眠期 |

### 5.2 半衰期（per-type，已修正 v2 反向错误）

```
H_danger    = 168h   (7  天)   危险必须快速被验证, 短 TTL
H_supply    = 720h   (30 天)   水源 / 营地状态会变
H_junction  = 1440h  (60 天)   路口偶有变化
H_scenic    = 2160h  (90 天)   风景中等寿命 (NZ 季节剧变, 不可设 360 天)
H_cairn     = 4320h  (180 天)  留言型最长, 但有上限
```

> **NZ 季节剧变约束**：秋色 / 雪山 / 春花的 scenic marker 不能设 360 天，否则展示信息和实地不匹配。

### 5.3 季节性休眠（处理冬季封山）

```
if is_winter(marker.region, current_date):
    Δt_effective = Δt_at_winter_start  # 冻结衰减
else:
    Δt_effective = Δt
```

> **数据来源**：DOC 公开的 Great Walks 季节封山日历（5 月底 - 10 月底）。区域级配置，无需用户操作。

### 5.4 核心公式

```python
# 寿命计算 (修复 v2 早赞惩罚 + 单赞陷阱)
LifeBoost = H_type × log10(L + 1) × 24    # L=0 时为 0; L=10 时 ≈ H × 24h
LifeLeft  = H_type + LifeBoost - Δt_effective

if LifeLeft < 0:
    visibility = "hidden"     # 隐藏, 作者可激活续命
else:
    # 展示得分 (HN 启发, 但分母用 H 归一化)
    DisplayScore = (L + 1) / ((Δt_effective / H_type) + 1) ^ G

# G = 1.8 (沿用 HN 调参, 经过 20 年验证)
```

**举例（H_supply = 720h = 30 天）**：

| 场景 | L | Δt_effective | LifeLeft | 状态 |
|---|---|---|---|---|
| 刚创建 0 赞 | 0 | 0h | 720h | 活 30 天 |
| 创建 30 天 0 赞 | 0 | 720h | 0h | 临界沉 |
| 创建 30 天 5 赞（最近 1 天前） | 5 | 24h | 1413h | 活 +59 天 |
| 创建 60 天 5 赞（最近 30 天前） | 5 | 720h | 717h | 活 +30 天 |
| 创建 90 天 50 赞（最近 5 天前） | 50 | 120h | 1820h | 活 +76 天 |

**关键性质**（v2 漏洞已修复）：
1. **L=0 时公式不爆炸**：t_last_like = t_create
2. **无早赞惩罚**：早赞晚赞结果对称（都靠 Δt_effective 而非 t_last_like 单点）
3. **单赞续命有上限**：1 赞贡献 H × log10(2) × 24 = H × 7.2h，约 5 天 vs v2 的 9 天，更短
4. **G=1.8 有根据**：HN 用 20 年的经验值

### 5.5 创建年限硬上限

```
if (current_time - t_create) > 730 天 (2 年):
    强制隐藏, 不论 L 多少
    通知作者: "此 marker 已 2 岁, 路况可能已变, 建议重新踏勘后续期"
    作者 100m 内可"重新创建"(t_create 重置)
```

> 解决"作者卸载 + 高赞 marker 永生"问题（场景测试 #5）。

## 6. 拥堵处理（好牧羊人小屋场景）

### 6.1 屏幕级密度上限

```
任何 zoom level + 任何屏幕区域:
  最多显示 K 个 public marker
  K = 20 (zoom > 14, 近距离)
  K = 8  (zoom 10-14, 中距离, 仅聚类)
  K = 0  (zoom < 10, 远距离, 不显示个体)
```

### 6.2 选择算法（按优先级层）

```
层 1 (绝对显示, 无视拥堵):
  - 用户自己的 personal cairn
  - 用户加入 group 的 group cairn

层 2 (强信号):
  - danger 类 (无视 DisplayScore, 全显示, 但同 50m 网格内 top1)
  - 创建 < 24h 的新 cairn (新鲜度保护期)

层 3 (按 DisplayScore 排序, 取 top K):
  - 同 50m 网格内每 type 仅显示 top 1 代表
  - 其余折叠为聚类点 "+N"

层 4 (溢出聚类):
  - 点击聚类点 → 列表视图, 按 DisplayScore + 距离双排序
  - 不丢失任何 marker
```

### 6.3 源头压缩（创建时干预）

```
用户创建新 marker, 30m 内已有同 type marker 时:
  → 弹出 "+1 已有 cairn" 推荐 (默认选项)
  → 用户主动点 "我要新建" 才创建
  → 防止好牧羊人式拥堵的源头治理
```

### 6.4 完成徽章（吸收 brag 需求）

> 来自 Agent 1 评审建议。

```
marker 可附加完成徽章: "我在此完成了 Routeburn Track"
  - 仅展示徽章 (路线名), 不暴露具体 GPX 轨迹
  - 满足 Strava 用户的 brag 需求
  - 不破坏 route 私有边界
```

## 7. 防刷（攻击经济学论证）

### 7.1 硬约束（不可绕）

**GPS 路过验证**：trackPoints 必须经过 30m 半径，且 trackPoints 来自真实运动状态（速度 / 方向连续性，已实现于 useTrackingStore Kalman filter）。

**攻击经济学**：
- 刷 1 票成本 = 真实开车 / 步行到 GPS 点 = 时间 + 油费 + 体力
- 刷 1 票收益 = 该 marker 续命 5 天 / 排名上升 X 位
- ROI 计算：偏远 marker 刷一票要驾车数小时往返，**ROI 严重为负**
- 唯一可行场景：城市公园 / 通勤路上 marker 顺路刷——但这种 marker 本来就是低风险类型（scenic / cairn）

**结论**：路过验证使 99% 攻击向量无利可图。

### 7.2 软权重（用户感知 0）

```
后台静默, 不影响用户体验:

设备指纹聚集: 同设备 ≥ 3 个账号在同 marker 投票 → 该批次权重 ÷ N
IP 时空聚集:  同 IP 1 小时内 ≥ 5 个账号投票 → 进入风控审核
节奏异常:     同账号 1 小时内 ≥ 10 票 → 该批次权重 ÷ 2
历史质量:     该账号留的 marker 平均得分 → 影响其投票权重 ±20%
```

> **新用户零门槛**：注册即可投票，软权重不可见。这避免了"新号限制打击积极性"问题（你第 8 点反馈）。

### 7.3 残余风险（接受）

**真朋友圈现实约定刷票**：5 个朋友真的开车去 marker 处刷票。
- 成本：每人数小时往返
- 收益：1 个 marker 排名提升
- 接受这种攻击——成本/收益比已不划算
- 风控聚集检测可在统计上识别此类事件

## 8. 作者心理保护（默认静默）

### 8.1 推送规则

```
默认全部 OFF (静默, 完全不打扰):
  □ marker 即将过期前 7 天通知
  □ marker 收到很多 Like 时通知 (每 +5 触发一次)
  □ marker 被举报时通知

用户在 Settings 主动 opt-in 才开启
```

> 严格执行你第 1-2 点反馈"系统不打扰"原则。

### 8.2 主动查看时显示

```
作者打开 "我的 Marker" 列表 / 点击自己的 cairn 时:
  ✓ 显示: Like 总数 (数字)
  ✓ 显示: 寿命剩余 (天数, 如 "还活 47 天")
  ✓ 显示: 举报汇总数字 (如 "1 举报")
  ✗ 不显示: 谁点的赞 / 谁举报 / 举报内容

  现场（< 100m 自己 cairn）:
    detail sheet 顶部显示行动按钮: "续期 / 编辑 / 删除"
    让现场修复变得可能, 但不打扰
```

### 8.3 不显示踩 / 负面投票数

> 因为根本没有"踩"。举报数 ≠ 踩，举报针对违规内容。

## 9. AR 投票交互（Cairn 独有差异化点）

> v2 完全空白，本节落地。

### 9.1 触发距离

```
AR 视角下:
  > 30m: marker 渲染但 detail 不可见
  < 30m: marker 渲染 + 标题 + Like 数字浮在 marker 上方
  < 15m: 加入 "Like" 手势可识别区
```

### 9.2 投票手势（避免误触）

```
方案 A (推荐): "凝视 + 双击空中"
  用户瞄准 marker (中心 reticle 对准, 持续 1.5s)
  → marker 下方出现 Like 按钮
  → 用户在屏幕任意空白处双击
  → 确认 Like, marker 上 +1 数字 + 一次粒子动画

方案 B (备选): "靠近 + 长按 marker"
  距离 < 5m 时, 长按屏幕上 marker 1.5s
  → 触觉反馈 + Like 完成
```

> 选择方案 A 因更"DS 化"——异步、克制、远程致意感。但需要 ARKit reticle 凝视实现。

### 9.3 视觉反馈

```
Like 完成后:
  - marker 上方数字 +1 (淡入 200ms)
  - 一道柔光从用户位置飘向 marker (粒子, 1s)
  - 触觉反馈 (Heavy Impact)
  - 不发出声音 (户外场景默认静音)
```

### 9.4 撤销手势

```
< 30m 内, 已 Like 状态:
  AR 内 Like 按钮变为 "Liked ✓"
  长按 1.5s → 撤销 (数字 -1, 反向粒子动画)
```

## 10. 数据隐私（NZ Privacy Act 2020 + GDPR 合规）

### 10.1 后端记录什么

```
public_marker_likes 表:
  - marker_id        (引用)
  - user_id_hashed   (SHA256 + salt, 不可逆推回 email)
  - device_fingerprint_hashed
  - ip_geohash       (geohash6, 1km 精度, 用于风控聚集检测)
  - vote_timestamp
  - vote_action      (like / unlike)
  - 不记录: 真实 IP / 真实 user_id / GPS 路过点位

public_marker_reports 表:
  - marker_id
  - reporter_id_hashed
  - reason_code       (枚举: spam / hate / privacy / safety_misinfo / cultural)
  - reported_at
```

### 10.2 保留期

```
风控数据 (设备指纹 / IP geohash): 90 天
投票事实 (Like 记录): 永久 (作者需要长期看到 Like 数)
举报记录: 7 年 (法务保留期)
```

### 10.3 用户权利（NZ Privacy Act 2020 第 7 原则）

```
用户可在 Settings:
  □ 导出我的所有投票记录 (JSON)
  □ 删除我的所有投票 (从 marker 减去 Like 数)
  □ 删除账号 (30 天冷静期, 投票仍计数但身份脱钩)
```

## 11. 申诉途径（极简）

### 11.1 投票申诉

**无**。因为只有 Like，无对抗性，无需申诉。

### 11.2 举报后被隐藏 marker 的作者申诉

```
marker 因 ≥ 3 个独立 IP 举报触发自动隐藏:
  → 推送通知作者: "你的 X cairn 被举报隐藏, 可申请复审"
  → 作者点 "申请复审" 按钮
  → 进入人工 review 队列 (单用户阶段开发者处理)
  → 复审期 7 天, 期间维持隐藏
  → 结果: 恢复 / 维持隐藏 / 转 group-only
```

### 11.3 路人举报恶意 marker

```
detail sheet 底部 "More" 折叠区:
  🚩 Report 按钮
  → 选原因: spam / hate / privacy / safety_misinfo / cultural
  → 进入人工 review 队列
  → 5 个独立 IP 举报触发自动隐藏 (避免单人滥用)
```

> **5 个独立 IP 阈值**：来自 Agent 2 元批判建议——防止小团体武器化举报。

### 11.4 单用户阶段（你自己）的角色冲突说明

```
当前阶段开发者 = 唯一审核员:
  - 你能看到举报人 + 被举报人的 hashed_id
  - 你不能看到真实 email / GPS 路径
  - 用户在 Privacy 政策中明确告知 "举报内容由开发团队审核"
  - 这是过渡期合规, 用户 > 1000 后引入 DOC 志愿者 moderator 体系
```

## 12. 冷启动配套设计（来自 Agent 1）

> public marker 反馈机制本身只解决"已有 marker 的展示与寿命"，**不解决新用户打开 app 的 30 秒空屏**。这部分配套必须做：

| 配套 | 作用 |
|---|---|
| **DOC 官方路线作为只读底图层** | 新用户打开看到 NZ 11 条 Great Walks，不破坏 route 私有边界（政府公开数据） |
| **marker 全境热力图 onboarding** | 首屏展示 marker 密度，让"集体行为"成为产品价值证明 |
| **完成徽章** | 见 §6.4，吸收 Strava brag 需求，不公开路线 |

> 这三件事是 public marker 机制的前置条件——没有这些，机制再精致也救不了冷启动。
