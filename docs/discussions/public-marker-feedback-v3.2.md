## 7. ⭐ 寿命公式 v2（重写，处理你第 4 点全部担忧）

> **核心改变**：从"最后 Like 重置时钟"改为"双时钟 + Like 时间衰减"

### 7.1 直观模型

```
力 1 (减寿，不可逆):
  从创建那天起，每天扣寿命
  → 解决"新建无人点赞永生"问题

力 2 (加寿，会衰减):
  每个 Like 都加寿命
  但 Like 自己也在贬值，旧 Like 几乎不值钱
  → 解决"近期 vs 远期权重"问题

力 3 (硬上限):
  无论怎么续，2 年自动归档
  作者 100m 内可手动重启 (t_create 重置)
```

### 7.2 Like 价值衰减（per-type τ 半衰期）

每个 Like 的当前价值随时间衰减：

```
单个 Like 价值 = exp(- Like 年龄 / τ)

τ = 类型半衰期 (见下表)

举例 τ = 60 天:
  当天 Like:  价值 1.00
  10 天前:    价值 0.85
  30 天前:    价值 0.61
  60 天前:    价值 0.37 (半衰期点)
  180 天前:   价值 0.05
  365 天前:   价值 0.002 (几乎没用)
```

### 7.3 per-type 参数

| 类型 | 基础寿命 (天) | Like 半衰期 τ (天) | 每"价值"续命 (天) |
|---|---|---|---|
| ⚠️ danger | 7 | 14 | 3 |
| 💧 supply | 30 | 30 | 5 |
| ↗️ junction | 60 | 60 | 5 |
| ⛰ scenic | 90 | 90 | 5 |
| 🪨 cairn | 180 | 180 | 5 |
| 🛡 DOC 官方 | max(类型, 365) | 不衰减 | 不适用 |

### 7.4 公式

```
当前热度 = Σ exp(- 该 Like 年龄 / τ)
                每个 Like 求和

寿命剩余 = 基础寿命 + 当前热度 × 续命系数 - 已活天数

if 寿命剩余 < 0:
  状态 = 隐藏 (作者可激活)
elif (今天 - 创建日) > 730 天:
  状态 = 强制归档 (硬上限)
else:
  状态 = 显示
```

### 7.5 验证（你担心的 case）

**Case 1：新建 0 赞 → 是否永生？**
- 热度 = 0
- supply: 寿命 = 30 + 0 - 1 = 29 天 → 30 天后必沉 ✅

**Case 2：100 赞但最近 90 天 0 赞 → 是否合理沉底？**
- 100 个 Like 都已 90 天龄，τ=30 (supply)
- 价值 = 100 × exp(-90/30) = 100 × 0.05 = 5
- 寿命 = 30 + 5×5 - 365 = -310 → **沉** ✅

**Case 3：30 天 100 赞最近还在涨 → 是否活？**
- 平均 Like 龄 15 天，τ=30
- 价值 ≈ 100 × exp(-15/30) ≈ 60
- 寿命 = 30 + 60×5 - 30 = 300 天 → **活很久** ✅

**Case 4：5 赞集中最近 1 天 vs 5 赞均匀 30 天**
- 集中: 5 × exp(-1/30) ≈ 4.84 → 续 24 天
- 均匀: 平均 15 天龄, 5 × 0.61 ≈ 3.05 → 续 15 天
- 集中更值钱 ✅（你的直觉对）

**Case 5：90 天 0 赞 → 突然 5 赞 死回生？**
- 5 × exp(0/30) = 5 → 续 25 天
- 寿命 = 30 + 25 - 90 = -35 → **仍沉**
- 要复活: 需 寿命剩余 ≥ 0
- 即 30 + 热度 × 5 - 90 ≥ 0 → 热度 ≥ 12 → **需 ≥ 12 个集中当天 Like 才能复活**
- 死回生门槛清晰 ✅

### 7.6 季节冻结的完整语义（subagent 漏洞修正）

```
冬季封山期间:
  - 已活天数 (days_alive) 冻结 ✅
  - Like 年龄 (like_age) 也冻结 ✅
  - 即整个 marker 进入"时间暂停"状态
  - 不偏向任何一方
```

### 7.7 修改窗口与投票触发真值表（subagent 矛盾修正）

| 当前状态 | 距离 | 路过窗口 | 24h 内 | 可投/可改 |
|---|---|---|---|---|
| 未投票 | <30m | — | — | ✅ 可投 |
| 未投票 | 30-500m | 7 天内经过 | — | ✅ 可投 |
| 未投票 | >500m | — | — | ❌ |
| 已投票 | <30m | — | — | ✅ 可改 |
| 已投票 | 30-500m | — | <24h | ✅ 可改 |
| 已投票 | 30-500m | — | >24h | ❌ |
| 已投票 | >500m | — | <24h | ✅ 可改（仅撤销） |

### 7.8 拥堵硬限制 vs "我要新建" 优先级（subagent 矛盾修正）

## 8. 拥堵处理（重审你第 5 点担忧）

你问：**用户真会 +1 吗？还是宁愿留自己的？**

### 现实评估

老 tramper（NZ 本地）：**90% +1**
- 知道好牧羊人有 200 个 cairn 没必要再加一个
- 看到现有 cairn 表达准确，乐意 +1

游客 / 新手：**40-60% 新建**
- 想留下"我也来过"痕迹
- 即使内容重复

→ **mark 爆炸是真风险**

### 修正方案（多层防御）

```
第 1 层 (源头压缩):
  创建时 30m 内已有 ≥3 个同 type marker:
    弹窗推荐 +1, 但允许"我要新建"
    新建按钮放在不显眼位置 (二级菜单)

第 2 层 (类型分流):
  "我也来过" 打卡冲动 → 引导用 完成徽章 (见 §9, 重新设计)
  不创建 marker, 只在已有 marker 上记录"路过"

第 3 层 (展示降密):
  屏幕级 K=20 上限 (即使创建了，展示时聚类)
  用户感知不到拥堵

第 4 层 (硬限制):
  同账号同 50m 范围内 7 天内最多新建 1 个 marker
  再多必须用 +1 或留言变体
```

### 即使如此，是否真能压住？

**诚实回答：不一定**。

如果实际 A/B 测试显示创建率 >50%（用户大量新建），需要紧急加：
- 创建提交按钮的等待时间（5 秒看现有 marker 摘要）
- 限制同区域 24h 内同类型创建数（per device）

## 9. 完成徽章重审（你第 6 点：徽章给谁看？）

### 你的质疑

### 修正后的"完成徽章"定位

**不是公开炫耀工具**，而是 **吸收"打卡冲动"的减压阀**：

```
用户走完 Routeburn 想 brag → 引导他贴徽章而不是创建新 marker

- 徽章存在自己的 profile / Stats 里，用户随时可看
- 朋友间 group 可分享

→ **这是反 mark 爆炸的辅助工具，不是社交炫耀**

## 11. 跑步模式（你第 3 点：跑步时阅读重要 / 高赞 marker）

```

  仅以下 marker 触发语音播报:

       - danger 类型: 无视热度直接播

       - 用户 public marker: 当前热度 ≥ 20 才播

> **DOC marker 不依赖热度**（subagent 修正）：因为 DOC Like 不衰减，热度会无限累积，按热度判断会让所有热门 DOC 永远播报。改为按 type 直接判断。

    → 给他们投票 Y/N
    → 多数决定

    → 给他们投票

    → 扩池: 改"附近 1km / 30 天内最近 30 用户"
    → 仍不足 → 升层 3

    → 默认自动转 group only (作者保留访问)
    → 通知作者: "marker 因偏远无人复审, 已降级 group only, 你可申请复活"
    → 作者点击"申请复活" → 升层 3 (人工)
    → 不强制人工, 减轻单用户阶段压力
```

### 复审防刷（subagent 修正）

```
复审投票本身也走 §12 软权重:
  - 设备指纹聚集 → ÷N
  - IP 时空聚集 → 标记可疑
  - 同团体集中投票 → 风控审核
→ 防止"复审被同团体刷"
```

```

  - 同一 marker 申诉 ≤ 2 次

## 14. ⭐ DOC 数据（你第 9 点：是否需要和用户 marker 区分？）

### 区分还是不区分？

**部分区分，部分统一**：

| 维度 | 决定 |
|---|---|
| 视觉 | ✅ **区分**（盾牌徽章 + "Source: DOC NZ"） |
| 数据形态 | ✅ 同（都是 marker） |
| Like 机制 | ✅ 同（都可 Like） |
| Like 续命 | ❌ **不同**（DOC 不衰减，是验证不是续命） |
| 寿命 | ❌ **不同**（DOC = max(类型, 365 天)） |
| 隐藏机制 | ❌ **不同**（DOC 不会被举报隐藏，仅替换或删除） |
| 算法层 | ✅ 同公式，参数不同 |

### 为什么部分区分？

- **视觉区分**：用户需要知道哪些是官方数据，建立信任。DOC 盾牌是合作署名义务。
- **机制不同**：DOC 数据是权威 baseline，不应被社区情绪化举报隐藏。但用户 Like 仍可表示"我验证过这个数据，准确"。
- **数据更新**：DOC 数据由 API 同步，过时数据自动替换，不需要算法衰减。

## 16. 隐私（NZ Privacy Act 2020）

### 后端表

```sql
public_marker_likes:
  marker_id
  user_id_hashed (SHA256+salt)
  device_fingerprint_hashed
  ip_geohash (1km)
  timestamp
  ✗ 不记录: 真实 IP / email / 原始 GPS

public_marker_reports:
  marker_id
  reporter_id_hashed
  reason_code (枚举, 见 §3)
  timestamp
```

### HMAC witness token

客户端 Kalman 验证用户路过 30m → 生成 HMAC token → 仅 token + marker_id + timestamp 上传，**后端不接收原始 GPS**

### 保留期

- 风控数据：90 天
- Like 记录：永久
- 举报记录：7 年（法务）

### 删除权（GDPR / NZ Privacy Act）

```
用户删除投票:
  → 该投票的 user_id_hashed 置 null (匿名化)
  → Like 计数仍保留 (避免恶意"先 Like 后删"攻击)
```

## 附录：Backend 公式

```python
# Like 价值衰减
def like_value(like_age_days, tau_days):
    return math.exp(-like_age_days / tau_days)

# 当前热度
def current_heat(likes, tau_days, now):
    return sum(
        like_value((now - like.timestamp).days, tau_days)
        for like in likes
    )

# 寿命剩余
def life_left(marker, now):
    if marker.is_doc:
        # DOC 不走衰减
        return None  # 永久（除非 DOC 数据替换）
    
    days_alive = (now - marker.t_create).days
    
    if days_alive > 730:
        return -1  # 强制归档
    
    if is_winter_frozen(marker.region, now):
        days_alive = (marker.winter_start - marker.t_create).days
    
    heat = current_heat(marker.likes, marker.tau, now)
    return marker.base_lifetime + heat * marker.boost_factor - days_alive

# 状态
def visibility(marker, now):
    if life_left(marker, now) < 0:
        return "hidden"
    return "visible"
```
