# 产品想法: 渐进式路径浮现动画

## 用户原话 (2026-06-25)

> "你在打开 APP 在后台的时候 他可以记录很多很多但是他那个时候耗电很低
>  当他打开 memory 的时候 假设他如果需要有一个 loading 的一个过程
>  那我们可以完全可以做一个动画 比如说我们一块块处理
>  那么它在 memory 上就是一块一块显示
>  那样用户技能看到它在慢慢地展示出自己的这个路径
>  又避免了一个 loading 的一个尴尬期"

## 关键洞察

把"加载延迟"包装成"探索仪式":用户不是在等 loading, 是在"见证自己的足迹被逐步揭开"。

这是 Zelda BoTW 塔解锁时地图慢慢展开的同一种产品语言 —— 把性能开销变成 game feel。

## 触发条件 (适用场景)

只在以下情况采用此方案:
- 打开 Memory 需要处理的数据 > 100k cells (raster rebuild ≥ 3s)
- 或后台积累了未导入的 Activity 数据 (chunk 处理)
- 或首次打开 / 长时间未打开后的首次

如果数据量小 (< 50k cells, rebuild < 1s) 直接一次性渲染,不需要分块动画反而显得多余。

## 实现思路 (待 spike J 确认是否需要)

1. 把待解锁的 cells 按时间顺序排序 (旧的先解锁)
2. 每 N ms 处理一批 (e.g. 500 cells / 100ms = ~5 chunks per second)
3. 每批触发一次 Skia raster 增量 redraw + ImageSource URI swap
4. 配合一个微妙的呼吸/扩散动效, 让"一块出现"看起来有意为之
5. 全部完成后正常进入 Memory

## 决策点

等 Spike N / J 结果出来后判断:
- N 显示后台耗电低 + J 显示导入很快 → **不需要此方案**, 直接一次性
- N 显示后台耗电高需要改 SLC + J 显示导入慢 → **需要此方案**, 把 loading 包装成探索

无论用不用, **保留这个想法在产品 deck 里**, 未来如果数据量爆炸 (海量 Activity 历史一次性导入) 就启用。
