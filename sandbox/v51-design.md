# v5.1 设计文档：流量保护机制（仅设计，未实施）

> 写于 2026-06-02。基于 v5 challenge 报告 (S1 季节性死寂误杀) 和用户产品反馈。
> **本文档为设计意图，未写入代码，等 subagent challenge 后再决定是否实施。**

---

## 一、问题诊断（v5 当前的根本错误）

### 错误的假设
v5 的 SUSPICIOUS / CRITICAL / DEAD 触发条件**默认每个 mark 都该有持续互动**：
- B 条件：累积 ≥ 10 但近 60 天 0 互动 → 进救命期
- C 条件：近 30 天 vs 90 天 sentiment 反转 → 进救命期
- D 条件：近 90 天 reports > likes → 进救命期

### 这种假设对偏远 / 季节性 mark 完全错
**没人去 ≠ 病症**。三种正常情况：

1. **冬季封山**：5-9 月雪山步道整季 0 人，标了 12 个赞的雪崩警告标 → 第 60 天进 SUSPICIOUS → 错
2. **偏远 mark**：年访客 50 人，6 个月可能 0 互动 → 完全正常
3. **小众路线**：Five Passes 全年 40 人走完，月流量 1 人不互动是常态

**这些 mark 都不是病症，应该按"正常寿命流失"自然衰减，而不是被算法判病。**

## 二、产品需求（用户反馈）

> "流量少的情况寿命应该有一个系数保护，应该比流量多的地方基础寿命更久 — 因为没人去续命。流量高的地方基础寿命就是基础。"

### 翻译成产品逻辑

| 流量水平 | 续命机会 | 基础寿命应该 |
|---|---|---|
| 高流量（每天多人路过） | 多 | 基础就够（base × 1.0） |
| 中流量（1-5 天 1 个） | 一般 | 基础就够 |
| 低流量（5-20 天 1 个） | 少 | **应给寿命加成** |
| 偏远（20+ 天 1 个） | 极少 | **应给更大寿命加成** |

**直觉对应**：
- Auckland Waitakere 一个步道 mark 30 天没人点赞 = **真有问题**
- Stewart Island 偏远 hut mark 30 天没人点赞 = **没人路过而已**

## 三、设计方案

### 1. 流量分档（trafficTier）

基于"历史互动密度"=（累积赞 + 累积举报）/（创建至今的天数），分四档：

| 档 | 互动密度 | 含义 |
|---|---|---|
| `remote` | < 0.05/天（20+ 天才 1 个互动） | 极偏远 |
| `low` | 0.05-0.2/天（5-20 天 1 个） | 低流量 |
| `medium` | 0.2-1/天（1-5 天 1 个） | 中流量 |
| `high` | > 1/天（每天多个） | 高流量（热门） |

**用全期累积**而不是近期，因为反映 mark 的**本质属性**（这地方就是没人去）。

### 2. 寿命加成（trafficLifetimeBoost）

```
remote:  base × 2.5
low:     base × 1.7
medium:  base × 1.0
high:    base × 1.0
```

整合到 `lifeLeftV4`：
```
adjustedBase = params.baseLifetime × authorBoost × ageDecay × trafficBoost[tier]
```

### 3. SUSPICIOUS 触发条件加流量保护

**核心原则：低流量 mark 不该被"死寂"或"持续衰退"逻辑误伤。**

| SUSPICIOUS 触发条件 | remote | low | medium | high |
|---|---|---|---|---|
| A. 急转（历史正向 + 近期负向） | **跳过** | 收紧 | 正常 | 正常 |
| B. 死寂过期（累积 ≥10 + 60 天 0 互动） | **跳过** | **跳过** | 正常 | 正常 |
| C. 持续衰退（近 30 vs 90 反转） | **跳过** | 收紧 | 正常 | 正常 |
| D. 近期举报为主 | 收紧 | 收紧 | 正常 | 正常 |
| E. 量级反转（累积 ≥30 + ratio<0.5） | 不变 | 不变 | 不变 | 不变 |
| F. brigade 疑似 | 不变 | 不变 | 不变 | 不变 |
| G. 持续争议（10+ 互动 ratio 0.4-0.65） | **要求 ≥30 互动** | **要求 ≥20 互动** | 正常 | 正常 |
| H. 渐进恶化 | 收紧 | 收紧 | 正常 | 正常 |

**"跳过"含义**：偏远/低流量 mark 即便满足这条触发条件，**也不进 SUSPICIOUS**。让它走正常寿命流失。

**"收紧"含义**：要求样本量更大或 sentiment 更极端才触发。

### 4. CRITICAL 触发条件加流量保护

**偏远 mark 不该轻易判病危**。

| CRITICAL 条件 | remote | low | medium | high |
|---|---|---|---|---|
| ratio < 0.40 + total ≥ 8 | **要求 ratio < 0.30 + total ≥ 15** | 收紧 | 正常 | 正常 |
| ratio < 0.45 + 近期负 | **要求 ratio < 0.30** | 收紧 | 正常 | 正常 |
| 量级大 + 累积负 | 不变 | 不变 | 不变 | 不变 |

### 5. DEAD 触发条件加流量保护

**偏远 mark 几乎不应该被算法判死**——除非有压倒性负向信号。

| DEAD 条件 | remote | low | medium | high |
|---|---|---|---|---|
| ratio < 0.15 + total ≥ 10 + 近30天0赞 | **要求 ratio < 0.10 + total ≥ 20** | 收紧 | 正常 | 正常 |
| 量级巨大 + ratio < 0.20 | 不变 | 不变 | 不变 | 不变 |

## 四、预期效果

### 修复的 case

1. **冬季封山雪崩警告**（v5 当前会误杀）→ 流量基本是 medium 但冬季季节性，需配合"季节性豁免"
2. **Stewart Island 偏远 hut**（v5 当前可能误判病危）→ remote 档自动保护
3. **Five Passes 老炮路线**（v5 当前 0/1 直接判沉）→ remote 档跳过 SUSPICIOUS / CRITICAL
4. **真实低流量好 mark**（v5 当前 base × ageDecay 自然衰减太快）→ 流量加成延长寿命

### 不影响的 case

- 高流量 mark（city / Great Walks 主线）：完全按原逻辑判，不该让 spam 借此活
- Brigade 攻击（条件 F）：不分流量都该识别
- 量级反转（条件 E）：累积大量 reports 不分流量都该识别

## 五、潜在副作用（你审）

1. **偏远 + 真垃圾 mark**：rate < 0.05 + ratio 0.30 (3 likes / 7 reports) 应该死，但流量保护可能让它活。需要在 CRITICAL 条件里保留"严重偏负"判定。
2. **流量分档的边界跳变**：rate=0.049 vs 0.051 → tier 从 remote → low → 寿命系数从 2.5 跳到 1.7。可能需要平滑。
3. **季节性高流量 mark（冬季 0 互动）**：年均互动密度高 → 算 medium/high tier → 60 天 0 互动仍触发 B 条件。需要额外的"季节性豁免"。

## 六、未涉及的事项

- **季节性识别**：本设计仅修流量保护，不涉及季节性识别（冬季 0 互动）
- **强心剂回退路径**：v5 challenge 提到的 M1，本设计不涉及
- **DEAD 30 天墓地期**：v5 challenge 的 P0 第 2 条，本设计不涉及
- **Wilson / revivedAt / isDoc 死代码**：实现 drift，本设计不清理

这些可以单独修，先聚焦"流量保护"这一个改动。

## 七、待 subagent challenge 的问题

1. 流量分档阈值（0.05/0.2/1）是否合理？
2. 寿命加成系数（2.5/1.7/1.0）是否合理？
3. SUSPICIOUS 各条件的"跳过/收紧"映射是否完备？
4. 是否有偏远 mark 应该被 SUSPICIOUS 但本设计漏掉的 case？
5. 流量保护和"季节性死寂"问题是否充分覆盖？
6. 流量分档用"全期"是否合理？季节性 mark（夏季高流量冬季 0）会被错判 medium/high？
7. 边界跳变会不会造成 mark 在两档间反复横跳？
