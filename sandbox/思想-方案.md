## PO 级决策清单（必须先决定）

### ⭐ 决策 1：DEAD 是不是真的不可逆？
- **选 A**：保持 DEAD 不可逆（原教旨）→ 需要付出"季节误杀 / 钓鱼误杀"代价
- **选 B**：引入 DORMANT 沉睡态（DEAD 之前有结构性休眠）→ 思想模型多一个状态
- **选 C**：DEAD 仍不可逆，但作者新建享受"位置免疫期"（同 GPS 24h 内不能被 brigade 杀）→ 折中

### ⭐ 决策 2：算法是否承担"识别商业 mark / 攻击者"的责任？
- **选 A**：是 — 算法引入 reporter / author 行为模式维度（隐式身份）
- **选 B**：否 — 算法只看"已观察到的互动"，反作弊交给独立的人工 / 风控层
- **选 C**：是，但只在"high-stakes"信号上启用（如 mark 即将 DEAD 之前一轮做反作弊复核）

### ⭐ 决策 3：偏远保护和趋势驱动谁优先？
- **选 A**：偏远保护优先 — 流量低 = 永远不判病（极端保守，纵容商业 mark）
- **选 B**：趋势驱动优先 — 任何反转信号都警觉（极端进攻，误杀偏远 mark）
- **选 C**：样本量做调和层 — 信号样本不足时两边都不动，等样本累积（中间路径）

**这三个决策不定，下面方案没法选。**

## 缺陷 1（矛盾 2）：DEAD 不可逆 vs 季节性 / 周期性 mark

**问题本质**：冬季封山 6 个月，年度活动一年 1 次——结构性死寂在医院模型里看起来和"真死"无差别，必然被推进 DEAD。

### 方案 A：DORMANT 沉睡态（在 DEAD 之前插一态）
- **思想层改动**：医院模型扩展为 `HEALTHY → SUSPICIOUS → CRITICAL → HEARTBEAT → DORMANT → DEAD`。DORMANT 是"结构性死寂中"，不可被算法判死，必须由"下一个流量循环出现"或"超过 N 个周期仍无流量"触发。
- **优点**：彻底解决季节误杀；产品语义清晰（"它没死，它在等季节"）；用户预期对齐 NZ 步道现实
- **缺点**：状态机变复杂；如何"识别下一个循环"本身是算法难题；可能被攻击者伪装（建一个 mark 然后假装它是季节性的）
- **攻击面**：攻击者建假 mark 不互动，永远停留 DORMANT 不被清理；需要"DORMANT 上限"做兜底
- **适用场景**：PO 决策 1 选 B

### 方案 B：救命期时钟"流量暂停"（不加状态，加规则）
- **思想层改动**：进入 SUSPICIOUS / CRITICAL 时记录"当时的流量基线"。观察期内 viewCount 跌至基线的 20% 以下时，时钟暂停（不计入观察天数）。流量回升时时钟继续。
- **优点**：状态机不变；DEAD 不可逆原则保留；实现层"不计天数"简单
- **缺点**：不能区分"季节性"和"商业 mark 长期没人来"——后者也会触发暂停，可能永远不死；mark 在 CRITICAL 时实际曝光仍在降低，季节回来的时候已被遗忘
- **攻击面**：攻击者把流量做低（不刷不互动）就能永远暂停时钟；商业 mark 钻这个空子
- **适用场景**：PO 决策 1 选 A（坚持 DEAD 不可逆）

### 方案 C：救命期跨年同期对比
- **思想层改动**：进入救命期时算法查"去年同期是否也是低流量"——如果是，判为周期性死寂，跳过这次救命期不消耗时钟；不是则正常救命期。
- **优点**：直接对症——周期性问题用周期性解；不引入新状态
- **缺点**：mark 创建第 1 年没有"去年同期"数据，对所有新 mark 不生效；冷启动期 12 个月几乎覆盖所有 mark；"是否是同期"本身要判（5-9 月封山 vs 6 月就开山，年份微差）
- **攻击面**：攻击者在创建第 1 年就攻击，新 mark 完全无保护
- **适用场景**：成熟系统（运行 2 年后）的优化方案，不能作为初版唯一手段

**推荐**：方案 A（DORMANT）+ 方案 C（同期比对）组合。先 DORMANT 解决最严重误杀，C 作为 DORMANT 进入条件判定。

**待 PO 决策**：✅ **是。这是产品决策不是算法决策**——"mark 能不能不死"是产品哲学。

## 缺陷 2（矛盾 1）：救命期固定 30 天 vs 偏远 mark 样本不足

**问题本质**：偏远 mark 30 天可能 viewCount = 2，统计上根本不能说明任何事。固定 30 天等于强迫算法在数据不足时下判决。

### 方案 A：救命期按流量分级（绝对天数 → 流量阈值）
- **思想层改动**：救命期不再以"30 天"为单位，而以"累积新增 view N 次"为单位。N 按基线流量分级（如：高流量 mark N=200 view，约 30 天；偏远 mark N=20 view，可能 12 个月）。
- **优点**：直接对症，统计学合理；偏远 mark 不会被仓促判决
- **缺点**：救命期长度对用户不可预测（"我这个 mark 还要观察多久？"）；商业 mark 可以让累积 view 慢慢凑够，长期处于 SUSPICIOUS 不杀不放；产品 UX 对作者不友好
- **攻击面**：攻击者刻意让 view 慢慢累积避免触发判决
- **适用场景**：PO 决策 3 选 C（样本量调和）

### 方案 B：救命期固定但加"低样本退出"（信号不足时回 HEALTHY）
- **思想层改动**：救命期到期时若样本不足（view < 阈值），不进 CRITICAL 也不维持 SUSPICIOUS，直接回 HEALTHY。下一次有反转信号再重新进 SUSPICIOUS。
- **优点**：天数固定可预测；偏远 mark 不会被冤杀；逻辑简单
- **缺点**："反复进出 SUSPICIOUS"对真有问题的偏远 mark 形成死循环——永远进不到 CRITICAL；商业 mark 完全免疫救命期
- **攻击面**：商业 mark 一辈子在 SUSPICIOUS ↔ HEALTHY 振荡，永不死
- **适用场景**：PO 决策 3 选 A（偏远保护优先）

### 方案 C：双轨救命期（保留 30 天 + 流量门槛二次确认）
- **思想层改动**：救命期仍 30 天到期，但要进入 CRITICAL 必须满足"30 天内累积 view ≥ K 次"。未达 K 则延长救命期到达 K 为止（最长 12 个月），到 12 个月仍没达到 K 则强制退出救命期回 HEALTHY。
- **优点**：兼顾"高流量按时判""低流量等数据"；有最长上限避免永久挂起
- **缺点**：12 个月上限本身是 magic number；上限到期时仍会发生"低样本判决"
- **攻击面**：攻击者控制流量在 K 以下慢慢拖到 12 个月

**推荐**：方案 C（双轨）。是 A 和 B 的折中，最贴合 NZ 步道现实。

**待 PO 决策**：⚠️ **半算法半产品**——"救命期可不可预测"是产品决策，"流量门槛 K 取多少"是算法决策。

## 缺陷 3（矛盾 3）：强心剂回退被刷

**问题本质**："看到正向波就回 SUSPICIOUS"的规则越宽防误杀越好，越严防攻击越好。思想没给"强心剂的真实性"判定。

### 方案 A：信号源多样性（强心剂的"独立用户数"门槛）
- **思想层改动**：强心剂回退条件不再看"like 数"而看"独立用户数"。回退要求：N 个不同用户在窗口期 like，且这些用户在该 mark 上无历史互动。
- **优点**：直接 counter 朋友圈刷赞；不引入身份维度仍能识别集中操作
- **缺点**："独立用户"也可以批量造（攻击者动员 30 个朋友各刷一次）；偏远 mark 可能凑不齐 N 个独立用户
- **攻击面**：组织化攻击仍可破，门槛 N 越高越难刷但偏远 mark 越难自救
- **适用场景**：PO 决策 2 选 B（不识别身份）

### 方案 B：强心剂需要"陌生人持续到场"而不是"瞬间爆发"
- **思想层改动**：回退条件改为"过去 N 天每天都至少有 1 个新陌生人 like"——要求时间分布而非数量。集中刷赞（一天 30 条 like）不触发回退；分散自然增长（每天 1-2 条持续两周）触发回退。
- **优点**：完美 counter "刷赞集中操作"；自然回退仍能触发
- **缺点**：偏远 mark 不可能每天都有人到场；偏远 mark 在 CRITICAL 后基本没救
- **攻击面**：攻击者可以让 30 个朋友分 30 天每天 1 个 — 但这种攻击成本极高，可接受
- **适用场景**：PO 决策 3 选 B（趋势驱动优先）

### 方案 C：分阶段回退（CRITICAL → SUSPICIOUS 严格，SUSPICIOUS → HEALTHY 宽松）
- **思想层改动**：回退分阶段，越接近 DEAD 的状态回退要求越高。CRITICAL → SUSPICIOUS 要求"独立用户 ≥ N + 时间分布 ≥ M 天"双重条件；SUSPICIOUS → HEALTHY 只要趋势平稳即可。
- **优点**：防刷重点放在最危险的回退（CRITICAL → SUSPICIOUS）；不影响正常自愈
- **缺点**：规则更复杂；具体阈值仍是 magic number
- **适用场景**：通用，最稳健

**推荐**：方案 C。攻击者愿意付高成本攻击的都是高价值目标（CRITICAL 边缘的 mark），把防御资源集中在那里。

**待 PO 决策**：❌ 算法决策。但 N、M 阈值需要看产品流量规模来定。

## 缺陷 6（漏 1）：作者声誉 / reporter 行为模式

**问题本质**：商业 mark + 慢渗透 + 钓鱼三种攻击都依赖"算法只看 mark 不看 user"的盲区。

### 方案 A：算法引入隐式 reporter 模式（不做身份认证，但识别行为）
- **思想层改动**：算法新增维度——"该用户在多少不同 mark 上 report 过""report 时间分布""目标 mark 是否同一作者"。某 reporter 集中攻击同一作者多个 mark = 信号；某 reporter 全平台只 like 不 report = 友军信号；某 reporter report 时间高度集中（凌晨批量）= 可疑。
- **优点**：直接 counter brigade、慢渗透、商业 mark；不破坏"无身份认证"约束（用行为模式替代身份）
- **缺点**：算法复杂度大幅提升；隐私敏感（即便是隐式画像）；冷启动用户没有行为历史
- **攻击面**：攻击者用多账号分散行为以躲避模式识别；但成本显著抬高
- **适用场景**：PO 决策 2 选 A

### 方案 B：算法只看 mark，反作弊另起独立层
- **思想层改动**：思想里明确写"算法只对 mark 信号负责，reporter 行为模式不在算法范围内"。商业 mark / brigade / 慢渗透由独立的反作弊系统识别后批量"标记"——算法收到"该 reporter 已被反作弊标记"的输入，自动衰减其权重。
- **优点**：职责清晰；算法保持简洁；反作弊可以人工 + 规则灵活迭代不影响算法
- **缺点**：反作弊层是独立工程，未必这版本能落地；空窗期内攻击者畅通无阻
- **攻击面**：反作弊不上线时，算法完全无防御
- **适用场景**：PO 决策 2 选 B

### 方案 C：算法只在 high-stakes 时启用 reporter 模式
- **思想层改动**：日常算法不看 reporter 模式；当 mark 即将进入不可逆状态（CRITICAL → HEARTBEAT 边界，或 HEARTBEAT → DEAD 边界）时，算法做一次"reporter 多样性复核"——若驱动 mark 走向 DEAD 的 reporters 在该作者其他 mark 上也集中报过，则回退一阶段。
- **优点**：节省日常算法成本；防御资源放在最关键的不可逆边界；不影响主流程
- **缺点**：复核结果可能延迟；需要保留 reporter-mark 关联数据
- **适用场景**：PO 决策 2 选 C，最实用

**推荐**：方案 C。Cairn 现阶段流量不足以支撑大规模 reporter 画像，但在 DEAD 之前做一次复核成本可控、价值最高。

**待 PO 决策**：✅ **是。"算法是否承担反作弊责任"是边界决策。**

## 缺陷 7（漏 2）：时间循环识别

**问题本质**：季节性、年度活动 mark 的"周期性死寂"被算法当成"真死寂"。

### 方案 A：跨年同期比对（被动识别）
- **思想层改动**：每个 mark 维护"过去 12 个月的月度流量曲线"。判死寂时对比"同月去年""同月前年"，若同期都是低流量则判结构性死寂，不进救命期。
- **优点**：完全自动；不需要作者声明；符合"算法基于已观察行为"原则
- **缺点**：第 1 年的 mark 没有历史可比；季节边界 mark（5 月底 vs 6 月初开山）误判
- **攻击面**：第 1 年新建的 mark 完全无保护

### 方案 B：作者声明 + 算法验证（主动 + 被动）
- **思想层改动**：作者建 mark 时可选标注"季节性""活动性""全年"。算法对季节性 mark 默认应用宽松规则；但若标注与实际流量模式不符（标了"全年"但模式像季节性，或反之），算法忽略标注。
- **优点**：第 1 年也有保护；作者意图可表达
- **缺点**：UX 多一步；攻击者标"季节性"逃避救命期；作者不一定知道自己的 mark 是季节性的
- **攻击面**：标注被滥用为逃生通道

### 方案 C：地理 / 路线分类自动推断
- **思想层改动**：基于 GPS 位置查询路线类型（高山步道 / 海岸 / 城市公园），高山路线 mark 默认应用季节性宽松规则。不需要作者标注，不需要历史数据。
- **优点**：第 1 年就有保护；UX 透明
- **缺点**：需要外部路线数据库；非高山的季节性场景（如年度活动）覆盖不到
- **适用场景**：NZ 国家公园 / DOC 步道有现成分类，可立即用

**推荐**：方案 A + 方案 C 组合。C 解决冷启动，A 解决长期精度。B 不要（攻击面大于价值）。

**待 PO 决策**：❌ 算法决策。但是否引入"作者标注"是 UX 决策。

## 缺陷 8（漏 4）：like / report 语义分层

**问题本质**：用户 like 一个 danger mark，是赞同"这里有危险"还是赞同"标记本身存在"？算法当前无法区分。

### 方案 A：按 mark 类型给 like / report 不同语义权重
- **思想层改动**：danger / supply 类 mark，like 默认表"赞同警告/资源"，report 表"内容失效"——report 权重显著高于 like（举报"假信息"代价大于点赞"提醒")。scenic / cairn 类 mark，like 表"喜欢"，权重对称。
- **优点**：单维度细化即可，思想模型不复杂
- **缺点**：所有 like 都被压权对 scenic 类不公平；type-by-type 的权重表是 magic
- **攻击面**：作者把商业 mark 标成 scenic 逃避高权重 report

### 方案 B：report 按 reason code 分层（已有理由列表）
- **思想层改动**：report 的固定理由列表本身分层——"内容已失效"（如水源干涸）权重最高；"位置偏移"中等；"信息不准确"低；"重复 mark"最低。这些权重影响病情判定速度而不是是否判病。
- **优点**：利用现有产品输入（理由列表）；细化但不引入新概念
- **缺点**：用户选择理由时随便选；理由权重表仍是 magic
- **攻击面**：攻击者全用最高权重理由刷

### 方案 C：不分层，但要求"report 多样性"
- **思想层改动**：不区分 like / report 语义，但要求 report 来自不同理由。同理由 report 集中（如 10 条都是"位置偏移"）权重不如分散理由（5 条不同理由）——前者更可能是商业刷举报，后者更可能是真问题。
- **优点**：counter 集中刷举报；不需要 type-aware 权重表
- **缺点**：真问题往往就是单一理由（水源干了所有人都报"水源干涸"），可能误伤
- **攻击面**：攻击者分散理由刷，需要更高组织成本

**推荐**：方案 B + 方案 C 组合。B 提供基础权重，C 加多样性约束。

**待 PO 决策**：❌ 算法决策。

## 缺陷 9（漏 3）：地理邻近

**问题本质**：相邻 mark 状态变化会带连带效应（一个 danger 修复后，旁边 junction 被误报"路标失效"）。

### 方案 A：邻近 mark 状态变化时给"宽容期"
- **思想层改动**：mark X 状态变化（如 CRITICAL → DEAD）时，X 周围 100 米内的 mark 在接下来 30 天内对负向信号降权。
- **优点**：直接对症；副作用小
- **缺点**：100 米和 30 天是 magic；对真有问题的邻近 mark 也降权
- **攻击面**：攻击者趁邻居死亡的宽容期对真问题 mark 刷举报，可获得豁免

### 方案 B：完全忽略地理维度（产品上声明"每个 mark 独立"）
- **思想层改动**：思想里明确"算法不考虑 mark 间相互影响。如果用户因为邻居 mark 错误报了，那本来就是产品需要解决的入口体验，不是算法责任"。
- **优点**：思想极简；职责清晰
- **缺点**：实际数据上误伤会发生；用户体验差
- **适用场景**：PO 认为这种连带效应少见，不值得引入维度

### 方案 C：邻近聚类视为一个"复合体"
- **思想层改动**：同一路线段（如 100 米内）的 mark 视为一个复合体，状态判定时看复合体整体趋势而不是单 mark。一座 danger 修复后，复合体趋势上升，旁边 junction 不会单独被判病。
- **优点**：从根本解决连带；语义上更接近"路况"而不是"单点状态"
- **缺点**：思想模型大改；mark 之间的依赖关系复杂；GPS 模糊导致聚类不稳定
- **适用场景**：长期方向，不是短期方案

**推荐**：方案 B（暂时忽略）。这个维度优先级最低，case 13 是真实但低频。可在 v6 引入方案 A。

**待 PO 决策**：✅ **是。"算法是否对地理上下文负责"是产品哲学。**
