# v5.1 流量保护设计 Challenge

> 审查时间: 2026-05-31
> 审查范围: `v51-design.md` (设计意图，未实施)
> 审查人: 产品 + 算法审查官

---

## 一句话评估

v5.1 在**保护偏远好 mark 不被"持续衰退"和"死寂"误杀**的方向上正确，但**用"全期累积互动密度"做分档**这个核心选择产生了一系列结构性漏洞——**新 mark 必偏远档、季节性 mark 永远高档、超长跨度 mark 被分母稀释、攻击者通过"克制互动"骗保护**——这些漏洞共同导致 v5.1 解决了一个 P0 (S1) 但引入了至少 2 个新 P0 (流量分档可被反向操纵 + 季节性 mark 仍然没救)。

---

## 设计完备性

### 1. 阈值合理性 (0.05 / 0.2 / 1 互动/天)

| 阈值 | 含义 | 问题 |
|---|---|---|
| 0.05/天 (20 天 1 个) | remote | **无 NZ 数据支撑**。设计文档没说"为什么 0.05"，只说"20 天才一个"。新西兰偏远 hut (例: Five Passes) 实际是"1 周 0-2 人路过"——若按"过路 view 不一定互动"算，可能 30-60 天才 1 个互动。0.05 偏松。 |
| 0.2/天 (5 天 1 个) | low | Auckland 城郊步道周末高峰、平日 0，年均刚好落在这条线，**与"高人气城郊"混档**。 |
| 1/天 | medium/high | Tongariro Crossing 类大众步道实际 5-50 互动/天，1/天的下限离实际太远，medium 档实际涵盖了"小众但活跃"和"半死不活"两类完全不同的 mark。 |

**核心问题**：阈值是直觉拍的，不是从数据里 cluster 出来的。NZ 步道分布是高度长尾的，三档可能比四档好；但若用四档，应该让 medium/high 之间用 5-10 而不是 1。

### 2. 系数合理性 (2.5 / 1.7 / 1.0 / 1.0)

| 系数 | 问题 |
|---|---|
| remote × 2.5 | scenic baseLifetime = 180 → **450 天基础**。叠加 official × 1.5 = 675 天。叠加 ageDecay (≤ 365 天 = 1.0) ⇒ **新建+偏远+official 的 mark 几乎不老化，攻击载体**。 |
| low × 1.7 | 在 0.049→0.051 跳变时 base 从 450 → 306 (32% 跳变)，过 sharp。 |
| medium/high × 1.0 | 把 medium 和 high 揉在一起的设计：高流量 mark 续命机会多，本应允许更短 base；但 v5.1 没区分。**等于把"流量大续命快"和"流量大但被刷"混在了一档**。 |

### 3. 触发条件映射完备性

设计表中 `B. 死寂过期` 在 remote/low **跳过**——但 B 是 v5 challenge 报告里 P0 (S1 季节性死寂误杀) 的根因。**这条修对了**。

但表中没覆盖：
- **new mark 流量分档过渡期** (mark 创建第 1-30 天 rate 极不稳定)
- **季节性 mark 全期 rate 失真** (设计文档自己在第 136 行承认未解决)
- **mark 累积量飙升后 rate 反而下降** (longevity penalty)
- **viewCount-based 流量** vs **interaction-based rate** 没对齐 (产品定义"流量 = AR 打开次数"，但设计用的是 (likes+reports)/days)

## 漏洞清单

### 🔴 P0 — 严重

#### V1. 流量分档定义与产品定义错位 — "互动密度" ≠ "流量"
**描述**: 产品现实里"流量 = 用户打开 AR 看到 mark 的次数" (即 `viewCount`)。但设计的 `trafficTier` 用的是 `(likes + reports) / days`——这是**互动密度**，不是流量。两者差异巨大：

- 一个网红打卡点：1000 view/天，2 like/月 (大家看了不点) → rate ≈ 0.07/天 → **被分到 remote**，享受 2.5× 寿命保护，**但它根本不是偏远 mark**。
- 一个真偏远 hut：年访客 30 人，10 个点 like → rate ≈ 0.027/天 → remote，正确。

**攻击场景**: 商业 mark 创建在城市公园 (高 view)，但作者刻意不点赞自己、雇水军不互动只看，rate 永远 < 0.05 → remote 档 → base × 2.5 × ageDecay (新建 = 1.0) = **450 天保护期，几乎免疫所有 SUSPICIOUS 触发**。

**严重性**: 🔴 — 这是设计的根本概念错位，所有下游漏洞都从这里派生。

**建议**: trafficTier 必须用 `viewCount / days` (真实流量) + `(likes+reports) / views` (互动转化率) 双指标。单用互动密度会被"看的人多但不点的人也多"的网红点和"看的人少且没人点"的真偏远点同档处理。

---

#### V2. 新 mark 必然被分到 remote — 1-30 天分母极小
**描述**: 一个新 mark 第 5 天有 1 个 like，rate = 0.2/天 → low；第 25 天还是 1 个 like，rate = 0.04/天 → **被分到 remote**。同一个 mark 在前 30 天里在 4 档之间漂移，且越老越偏远。

**攻击场景**:
1. 攻击者创建商业 mark，刻意只让自己 1 个朋友 like (制造"曾经有人 like"的合法外观)
2. 静置 30-60 天，rate 自然降到 < 0.05 → remote 档
3. 此时再开始投放，**所有 SUSPICIOUS A/B/C 都跳过**，所有 CRITICAL/DEAD 阈值都被收紧
4. 完美绕过 v5 的全部反垃圾机制

**严重性**: 🔴 — 直接破坏 v5 的所有救命期触发条件。

**建议**: 流量分档必须有"成熟期门槛"，例如 mark age < 60 天或 total < 5 时不分档 (走 medium 默认)；否则新 mark 自动进入低档保护期就是攻击窗口。

---

#### V3. "克制互动"反向骗保护 — 攻击者刻意不点赞自己
**描述**: 设计假定"互动少 = 偏远 = 应该保护"。但攻击者读了源码后会反向操作：

**攻击场景 A — 静默商业 mark**:
1. 攻击者建一个商业 supply mark
2. 不让任何人 like，让 5 个真人 view (满足 viewCount > 0 看似真实)
3. rate = 0/天 → remote 档
4. base × 2.5 × ageDecay → 450 天近乎免疫
5. 即使有 1-2 个真用户 report，因 G/H 收紧到 ≥ 30 互动，永远不触发 SUSPICIOUS

**攻击场景 B — 限速刷量**:
1. 攻击者建多个商业 mark
2. 每 30 天精准让 1 个水军 like，rate ≈ 0.033/天 → 永远 remote
3. 收益: 在 v5 里这种 mark 早被 ageDecay 自然衰减了；v5.1 给了它 2.5× 续命

**严重性**: 🔴 — v5.1 直接把"低互动"等同于"偏远好 mark"，但**低互动也可能是低质 mark 没人想互动**——算法无法区分。

**建议**: 区分"积极不互动" (view 高 like 低，可能是低质) 和 "没人路过" (view 也低)。单看 (likes+reports)/days 必然误判前者。

---

### 🟡 P1 — 中等

#### V4. 边界跳变 30%+ — rate=0.049 vs 0.051 寿命差 30%
**描述**: 设计文档第 132 行自己承认："rate=0.049 vs 0.051 → tier 从 remote → low → 寿命系数从 2.5 跳到 1.7。可能需要平滑。"——但**设计没有平滑方案**。

**实际后果**:
- 一个 mark rate 在 0.045-0.055 间漂移 (一个新互动到来即可跨边界)
- 寿命在 base × 2.5 (450 天) ↔ base × 1.7 (306 天) 间反复跳
- `markerStatusV4` 是无状态判定，每次调用基于实时 rate → mark 状态会"闪烁"
- UI 层显示的 lifeLeft 会突然 -144 天或 +144 天，用户体验异常

**严重性**: 🟡 — 不致死但破坏算法稳定性，且边界 mark 数量不少。

**建议**: 用平滑插值 boost = lerp(2.5, 1.7, (rate - 0.05) / 0.15) 等方式，或用滞后 (hysteresis) 防抖。

---

#### V5. 季节性 mark 仍然没救 — 设计文档已承认
**描述**: 设计第 136 行明确："季节性高流量 mark (冬季 0 互动) 年均互动密度高 → 算 medium/high tier → 60 天 0 互动仍触发 B 条件。需要额外的'季节性豁免'。"

**也就是说**: v5.1 修了"全年偏远 mark"的死寂误杀，但**没修原 v5 challenge 报告 P0 中真正最危险的 case** —— S1 描述的就是"DOC 雪崩警告 + 冬季 60 天 0 互动 + DEAD 不可逆"。

**这个 mark 全年互动密度是 high (夏季活跃)，所以 v5.1 给它 medium/high 档 = 没保护，B 条件照常触发，照常死。**

**严重性**: 🟡 — 实际上是 🔴 (生命安全)，但因为 v5.1 明确说"不涉及季节性"，定为 🟡。但这等于 **v5.1 没解决它声称要解决的核心问题** (S1)。

**建议**: 流量分档应基于"有互动月份的密度"而非"全期密度"。或者保留 v5.1 但明确标注"S1 仍未解决，需 v5.2 季节性识别"。

---

#### V6. 超长跨度 mark 被分母稀释 → 假偏远档
**描述**: 一个 5 年老 mark，total = 100 likes + 10 reports = 110 互动，rate = 110/1825 = 0.06/天 → **low 档** (接近 remote)。但这个 mark 实际是"曾经热门后冷却"，不是偏远。

**问题**: 给了它 1.7× 寿命加成，但它本来正常老化是合理的产品行为。

**攻击场景**: 攻击者捡 5-7 年老 mark (如已经被遗弃的早期商业刷的)，靠 rate 已落到 low/remote 档，加 base 1.7-2.5×，复活成"长寿垃圾"。

**严重性**: 🟡 — 攻击成本高 (需找老 mark)，但确实存在。

**建议**: 流量分档应有时间窗口，例如近 365 天的 (likes+reports)/365；超过 mark age 取 mark age。

---

#### V7. DOC + remote 双重保护 → 寿命过长
**描述**: official (1.5×) × remote (2.5×) × ageDecay (1.0) = base × 3.75。scenic 类型 base = 180 → **675 天保护期**。danger 类型 base = 90 → **337 天**。

**问题**: 该不该这么久？产品方需要决定。如果一个被错误声明 official 的商业 mark 拿到这个 boost，它实际上**穿越了 ageDecay 的 365 天保护期 + 流量保护**，几乎不死。

且 commercial_spam (0.5) × remote (2.5) = 1.25——**比普通 user (1.0) × medium (1.0) = 1.0 还久**。商业刷子在偏远档反而比普通用户老 mark 寿命长，明显反直觉。

**严重性**: 🟡 — 设计 mismatch，需要叠加规则 cap 总 boost。

**建议**: 总 multiplier cap，例如 `min(authorBoost × trafficBoost, 3.0)`；commercial_spam 应是绝对压制，不应被 traffic boost 救。

---

### 🟢 P2 — 轻微

#### V8. 触发条件映射表里 G "持续争议" 在 remote 要求 ≥ 30 互动 — 偏远 mark 永远到不了 30
**描述**: 设计表第 87 行：G 在 remote 档要求 ≥ 30 互动。但 remote 定义就是 < 0.05/天，5 年才能积累 91 个互动。**实际上等于 remote 档免疫 G 触发**。是否合理？争议 mark 在偏远地方就不会被识别为争议 → 也许合理，但应明示。

#### V9. 表中 E (量级反转)、F (brigade) 标 "不变" — 但 brigade 在偏远地方更难触发
**描述**: F 要求"近 14 天 5+ reports 0 likes"。在 remote 档，14 天内有 5+ 任何互动几乎不可能 → F 在 remote 等同失效。设计写"不变"等于失效，应该说明。

#### V10. v5.1 没涉及 v5 challenge 的 P0 第 2 条 (DEAD 30 天墓地期)
**描述**: 即便 v5.1 让偏远 mark 不进 SUSPICIOUS，但若 v5 中其他路径仍能让它进 DEAD (如累积 30+ 后 ratio 跌)，DEAD 不可逆 = 仍永久消失。**v5.1 + DEAD 不可逆 = 部分修复 P0**。

## 与 v5 challenge 的关系

### 解决了
- **S1 部分** — "全年偏远 mark 的死寂误杀" (rate 始终 < 0.05) 被修复
- **S4 部分** — 持续争议 G 在 remote/low 档跳过/收紧，复杂地标在偏远地区不会一刀切被杀

### **没解决** (v5.1 声称要解决但实际没有)
- **S1 核心 case** — "季节性 DOC 雪崩警告 mark"，因夏季活跃，年均 rate 落在 medium/high，B 条件照常触发 (设计第 136 行自己承认)
- **DEAD 不可逆** — v5.1 不涉及

### 引入的新漏洞
- **V1** 流量定义错位 (互动密度 ≠ 流量)
- **V2** 新 mark 必偏远档 → 攻击窗口
- **V3** 攻击者克制互动骗保护
- **V4** 阈值跳变
- **V7** boost 叠加爆炸

### 不影响
- **S2** authorRole 无验证 — 仍是平台职责
- **S3** 慢速渗透投票 — 在 medium/high 档照常被攻击
- **M1-M6, L1-L10** — 大部分不变

## 建议的"应改进"

1. **重新定义 trafficTier**：用 `views/days` 而非 `(likes+reports)/days`。互动密度做辅助指标但不主导分档。
2. **加成熟期门槛**：mark age < 60 天 OR total < 5 → 强制走 medium 默认，不进 remote 保护。
3. **平滑边界**：用 lerp 或 hysteresis 替代硬阈值跳变。
4. **boost cap**：`finalBoost = min(authorBoost × trafficBoost, 3.0)`，commercial_spam 不享受 traffic boost。
5. **流量分档用近期窗口**：近 365 天的 rate；老 mark 不被全期分母稀释。
6. **必须配合季节性识别一起做**：v5.1 单独上线只解决了边缘 case，最危险的 S1 主 case 没解决。建议捆绑发布。
7. **明确 G/F 在 remote 等于失效**：在文档里写出来，让产品方知道偏远地区算法盲区。

## 建议的"可接受"

- **V8 (G 在 remote 永远不触发)**：偏远地方争议 mark 本就少，可接受。
- **V9 (F 在 remote 失效)**：偏远地方 brigade 攻击成本极高，几乎不会发生，可接受。
- **V6 (超长跨度 mark)**：攻击成本太高 (需找 5+ 年老 mark)，可接受但需监控。

## 最终判断

**是否值得实施 v5.1: 🟡 conditional — 不推荐当前形态实施**

实施前必须解决：
1. **V1 (流量定义错位)** —— 这是根本问题，不修则整个分档机制方向错了
2. **V2 (新 mark 必偏远)** —— 直接攻击窗口，必修
3. **V5 (季节性 mark)** —— v5.1 声称要解决但实际没有，要么改设计要么明示局限
4. **V7 (boost 叠加)** —— 加 cap，否则 commercial_spam 反而比普通 user 长寿

**推荐路径**:
- **A. 先做 v5.2 季节性识别**，再上 v5.1 流量保护——顺序反了会让问题更复杂
- **B. 简化 v5.1**：只保留 "B 条件 (死寂过期) 加流量豁免" 这一条最关键的修复，其他先不做。最小改动解决 S1 边缘 case，不引入 V2/V3/V7 这些新漏洞
- **C. 不实施**：当前 v5 chaos-monkey 100% 是在 chaos-monkey 输入分布下的；S1 是真实生产场景的边缘 case，需要先用真实季节性 mark 数据 replay 确认问题严重性，再决定是否值得引入分档机制

**我的倾向**: 选 **B**。最小改动 (B 条件加 "近 365 天有过 like 则跳过") 可以解决 S1 大部分 case，不需要引入 trafficTier 这个充满漏洞的新概念。

---

## 一句话总结

v5.1 把"流量 = 互动密度"这个概念错位带进了算法核心，制造了"克制互动 = 享受保护"的反向激励，**值得修但不该用当前设计修**。
