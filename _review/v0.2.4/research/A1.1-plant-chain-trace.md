## 关键发现总结

### ✅ 当前流程是正确的(v0.2.4)

整个调用链使用 ARKit World 坐标,而非 GPS:

1. **RN 端 (ARScreen.tsx:835-1112)**
   - 读 GPS: `lastCoord` 来自 `expo-location`
   - 读 ARKit: `arFrame.camera/origin/groundY`
   - **关键**: 用 `arFrame.origin` (GPS at session start) 作为参考点投影
   - 输出: `unitySpawnPos {x,y,z}` 是 ARKit world 坐标

2. **Native Bridge**
   - 直接发送 ARKit world coords 到 Unity
   - 不再转换,保持精度

3. **Unity 端 (PortalSpawner.cs:363-809)**
   - 接收 `data.x/z` 是 ARKit world
   - 地面检测: `GroundYResolver.QueryGroundY()` 查询 **Tier-A ARKit plane**,NOT GPS altitude
   - **ARAnchor 挂载**: `arRaycast.Raycast()` → `AttachAnchor(plane, pose)` 同步
   - Container 立刻 parent 到 anchor: `container.SetParent(anchorOnSpawn, false)`

### 🔴 飞天根因清单(3-5 个最可能)

| 根因 | 代码位置 | 状态 |
|---|---|---|
| 1. sessionOffset per-frame virtualOrigin (v210) | RN bridge | ✅ v0.2.4 fixed |
| 2. ARAnchor 挂载延迟 1s (v186) | PortalSpawner:336 | ✅ v0.2.3 fixed |
| 3. **无平面时 fallback free-floating** | PortalSpawner:620-627 | ⚠️ 仍存在 |
| 4. groundY = camera.y - 1.3m (v206 前) | PortalSpawner:370 | ✅ v0.2.3 fixed |
| 5. **arOrigin 初始化前用 live GPS** | UnityAROverlay:802 | ⚠️ 不够稳定 |

### 🎯 三大仍存在的风险

**1. 无平面无 LiDAR 时 container free-floating**(PortalSpawner:620-627)
- 墙壁/天花板/室内无纹理 → 无 ARKit plane detection
- Container 无 parent anchor → ARKit frame 漂移时跟着飘
- 下次冷启 AR session → 位置完全错位

**2. arOrigin 初始化延迟**(useMarkerStore)
- 需要 GPS lock 30s+ 以后
- 之前 plant 的 marker 用 live GPS 参考 → 不稳定

**3. PlaneDetected 仍可能误认 tabletop**(虽已改进)
- 多层楼房/架子房间
- 底-三分位 filter 还不够完美
